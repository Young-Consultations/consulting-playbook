# Publication readiness gate (candidate; not deployed)

Implements the owner-approved cost-bearing prerequisite policy in [organization #77](https://github.com/Young-Consultations/.github/issues/77) and its [shared policy candidate](https://github.com/Young-Consultations/.github/pull/121). This candidate targets the unpublished v5.0.0 release and does not change the existing immutable v4.0.0 adapter or activation. The new gate runs after existing Git push metadata, dry-run and sandbox checks and before provider login/model execution. Verify-only and verified owned-draft reuse remain unchanged.

For future separately approved adoption, use the exact protected environment `consulting-playbook-codex`. Configure `PUBLICATION_POLICY_REVISION` as an owner-maintained protected environment variable and `PUBLICATION_READINESS_EVIDENCE` as a protected environment secret, not repository-level fallback or task input. Evidence must be independently reviewed by the operator after a separately authorized successful bounded no-model publication test with the exact publisher. Record v1 fields described in the organization policy. Never print the record or fingerprint. Rotation, release or policy binding mismatch and evidence older than 30 days fail closed. Update the policy revision or remove evidence on permission or settings drift; a future permission revocation can still occur after a check.

The adapter isolates the readiness secret alongside existing credentials. No new secret or policy value has been provisioned; no live canary is included or authorized. Do not activate or publish this candidate without reviewed release coordination and explicit readiness acceptance. Existing dry-run and result credential preflight remain mandatory. The shared validator and tests are byte-bound in the existing conformance pin; fixture version and payload contract are unchanged. Existing PR-create retries remain a separate recovery issue.

The offline-only canary model and tests use synthetic ownership snapshots and effect counters. They cannot create real artifacts or generate valid readiness evidence. The original simulator has no live transport. The protected transport candidate below remains subject to separate approval and release acceptance.


## Protected live transport candidate (not authorized or deployed)

The manual publication-canary workflow is restricted to the exact future adapter tag, first attempt, existing consulting-playbook-codex environment, configured owner, immutable control-plane registry and published runtime attestation. No current tag or settings are changed. The protected environment must have appropriate reviewer/ref restrictions and no repo/org fallback for the new authorization variables; the runtime cannot prove those settings, so review them separately before any dispatch. The owner must verify that the draft/push cannot trigger paid automation or deployments before authorizing it. No provider, router or result-writer credential is passed.

Proposed owner-managed environment variables (not provisioned): PUBLICATION_CANARY_APPROVER (exact owner login), PUBLICATION_CANARY_PUBLISHER (actual user login of TARGET_PUBLICATION_TOKEN), PUBLICATION_CANARY_AUTHORIZATION (exact colon-separated automation-safe:canary_id:adapter_sha:control_plane_sha:base_sha:policy_revision:publisher_login). The authorization prefix attests automation was reviewed, not a machine-verified guarantee. Existing CODEX_AUTHORIZED_CONTROL_PLANE_SHA and PUBLICATION_POLICY_REVISION must match. No permission expansion is implied. A separately approved dispatch must supply that same ID and main base and confirmation publish-one-draft.

The API transport uses a single harmless JSON marker added to docs/ai-sdlc-canary, one Git tree and commit, one atomic create-only ref and at most one draft-PR create attempt. This deliberately substitutes the Git Data create-ref API for a normal Git push, eliminating overwrite races; it does not prove actual Git transport. Existing production per-execution Git push dry-run remains required. Permission metadata, exact approved main, tag, immutable registry, publisher identity, branch parent and marker diff, PR author, draft status, head/base, body and URL are checked. HTTP requests are bounded, redirects prohibited, errors sanitized. API ambiguity stops; only a readback may reconcile a PR. An existing branch without a verified owned draft permanently blocks further creation for that identity, including reruns; the owner must reconcile, not delete and reuse an identity. A newly created branch can remain after a failure, as can unattached Git objects; no automatic cleanup. The earlier offline model's owned-branch resume is intentionally not permitted by the live transport.

Readback of an existing or reconciled draft does not establish current PR-write capability. Even a fresh verified result requires human review of the exact credential and policy before separate protected readiness provisioning. The transport never outputs the token/fingerprint or a readiness-eligible record. Operator must not rotate or substitute the publisher between proof and attestation. No real execution, tag or credential changes are authorized by this candidate.

Offline tests call the real orchestration with fake API state and trap real HTTP, socket and subprocess effects. The test suite is included in the exact conformance pin and CI. The workflow is manual-only; CI does not dispatch it.
